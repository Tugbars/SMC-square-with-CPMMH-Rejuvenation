Prior Selection for Production

How to choose priors when you don't know the true parameters, and what to do when priors don't match reality

The Prior Truncation Problem

If your prior bounds exclude the true parameter values, the filter cannot find them. The posterior piles up at the boundary:

Prior: mu_base ∈ [-2, 0]
True:  mu_base = -4.2

     Prior density
         ▲
         │    ┌────────────┐
         │    │            │
         │    │  ALLOWED   │
         │    │   REGION   │
         │    │            │
         └────┴────────────┴──────────────────▶ mu_base
             -2            0
              ▲
              │
         Posterior piles up here
         (can't go lower!)
                                    TRUE VALUE
                                        ↓
         ─────────────────────────────(−4.2)───

Symptoms of Prior Truncation

  • Posterior mean very close to prior boundary
  • Posterior std suspiciously small (artificially constrained)
  • Z-scores explode when you know ground truth
  • NLL remains elevated even after convergence
Real Example

With priors mu_scale ∈ [0, 1] and true value 2.8, the estimate got stuck at 0.69 with 75% error — the filter literally couldn't reach the truth.

Two Philosophies

Philosophy 1: Wide Priors (Robust)

Use very wide, weakly informative priors that cover any plausible market regime:

// "I don't know much, but I know physics"
// Vol can't be negative, rho must be < 1, etc.

PriorBounds wide = {
    .mu_base_min  = -10.0f,  // 0.7% vol
    .mu_base_max  = 0.0f,    // 100% vol
    .mu_scale_min = 0.0f,
    .mu_scale_max = 6.0f,    // ~400× vol increase possible
};
✓ Pros
  • Robust to unknown regimes
  • Won't miss true values
  • Simple — no adaptation logic
  • Safe default choice
✗ Cons
  • Slower convergence
  • Needs more data (T > 3000)
  • Needs more particles
  • May explore implausible regions

When to use: Production systems, unknown market regimes, when robustness matters more than speed.

Philosophy 2: Adaptive Priors

Start with reasonable priors based on domain knowledge, but detect and respond to boundary hitting:

1. START with "typical market" priors
   mu_base ∈ [-4, -1]    // 10-60% annual vol
   mu_scale ∈ [0, 2]     // up to 3× vol in stress

2. RUN SMC² and monitor posterior

3. DETECT boundary hitting:
   posterior_mean - 2σ < prior_min  →  hitting lower bound
   posterior_mean + 2σ > prior_max  →  hitting upper bound

4. RESPOND:
   Option A: Expand bounds and re-run
   Option B: Flag result as unreliable
   Option C: Use drift to gradually migrate
✓ Pros
  • Faster convergence initially
  • Domain knowledge helps
  • Tighter posteriors
✗ Cons
  • Complex logic
  • May need re-runs
  • Risk of missing regimes

When to use: Research, known stable regimes, when you have good domain priors.

Recommended Prior Bounds

Log-Volatility Scale Reference

Understanding what μ_base values mean in terms of annualized volatility:

-6.0 5% Very calm (bonds, low-vol stocks)
-4.0 14% Normal equity vol

PriorBounds production = {

Boundary Detection

Implement runtime checks to detect when posteriors are truncated:

bool check_truncation(
    const float* mean,
    const float* std,
    const float* prior_min,
    const float* prior_max,
    float margin  // e.g., 0.05 for 5%
) {
    for (int p = 0; p < N_PARAMS; p++) {
        float range = prior_max[p] - prior_min[p];
        
        // Check if 2σ interval hits boundary
        if (mean[p] - 2*std[p] < prior_min[p] + margin*range) {
            printf("[WARN] Param %d at lower bound\n", p);
            return true;
        }
        if (mean[p] + 2*std[p] > prior_max[p] - margin*range) {
            printf("[WARN] Param %d at upper bound\n", p);
            return true;
        }
    }
    return false;
}

Response Strategies

Strategy A: Expand & Re-run

if (truncated) {
  bounds.min[p] *= 1.5f;
  smc2_reset(state);
  // Re-run
}

Good for batch processing where latency is acceptable.

Strategy B: Flag & Continue

if (truncated) {
  result.confidence = LOW;
  // Continue cautiously
}

Good for real-time where you can't re-run.

Strategy C: Increase Drift

if (truncated) {
  Q[p] *= 2.0f;
  // Let drift migrate
}

Good for streaming mode with drift enabled.

Prior Initialization

Option 1: Sample from Prior

for (int j = 0; j < N_theta; j++) {
    theta[j][p] = uniform(prior_min[p], prior_max[p]);
}

Pros: Unbiased, explores full space
Cons: Many particles start in implausible regions

Option 2: Concentrated Start

float mid = (prior_min[p] + prior_max[p]) / 2;
float range = prior_max[p] - prior_min[p];
theta[j][p] = mid + 0.1f * range * randn();

Pros: Fast initial convergence
Cons: May miss true value if prior midpoint is wrong

Option 3: Warm Start (Recommended for Recalibration)

float* prev = hcrbpf_get_params();
theta[j][p] = prev[p] + jitter_std[p] * randn();

Pros: Best for recalibration — starts near known-good region
Cons: May be trapped if previous params were wrong

Recommendation

For a recalibration system: Use warm start in normal operation, but fall back to wide prior sampling when NLL excess indicates severe drift.

Domain-Specific Prior Elicitation

Questions to ask when setting priors:

Volatility Level (μ_base, μ_scale)

  1. What's the lowest realistic annualized vol for this asset? → μ_base_min
  2. What's the highest vol observed historically? → μ_base + μ_scale max
  3. How much can vol increase during stress? → μ_scale_max

Example: SPY (S&P 500 ETF)

  • Lowest: ~8% (2017 calm) → μ_base_min ≈ -5.0
  • Highest: ~80% (March 2020) → μ_base + μ_scale ≈ -0.4
  • Stress multiplier: ~10× → μ_scale_max ≈ 4.0

Regime Dynamics (ρ, σ_z)

  1. How long do vol regimes typically last? → ρ
  2. How quickly can regimes switch? → σ_z

Example

  • VIX mean-reversion half-life: ~20-40 days → ρ ≈ 0.95-0.98
  • Flash crash regime switch: <1 day → σ_z up to 0.2

Bottom Line

For a recalibration system that must handle unknown regimes, use wide priors and accept slower convergence. The drift mechanism helps explore even if you start in the wrong region. Always implement boundary detection as a safety check.
